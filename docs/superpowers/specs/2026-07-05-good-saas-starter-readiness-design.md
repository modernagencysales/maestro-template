# Good SaaS Starter Readiness Design

## Goal

Make Maestro Template feel like a serious B2B SaaS starter, not only a strong
technical reference. The first-run path should show a builder what exists, what
is fake, what is ready, and what to do next without reading the whole repo.

## Current State

The repo is technically strong: `review:readiness`, `review:completion`, full
verification, hosted smoke, Confect/Effect contracts, generated headless
surfaces, fake providers, and the hosted Notion Kit reference app are in place.

The remaining gap is productization:

- The reference app reads like a diligence document more than a starter console.
- The Day-0 loop is documented, but the UI does not make that loop obvious.
- `template:doctor -- --mode fake` is useful only after `template-instance.json`
  exists; the quickstart docs should make that dependency unmistakable.
- Some maturity/backlog docs still describe older porting status and can confuse
  a builder about what is currently real.

## Desired Experience

A new builder should be able to:

1. Open the app and immediately see a SaaS starter console.
2. Understand the Day-0 loop: generate instance, seed demo, check fake provider
   posture, inspect workflow proof, then customize one domain noun/capability.
3. See which surfaces are real and reusable: web shell, Brain, workflow,
   capabilities, agents, API, CLI, MCP, provider posture, security gates.
4. See honest fake/test/live status without live credentials or secret values.
5. Follow docs that match the app and command behavior.

## Architecture

Keep the existing Notion Kit shell and TanStack Start route shape. Add starter
readiness as a view-model and document-section layer inside the sample app,
using the existing `NotionDocumentPage` renderer and app shell.

The first slice should not introduce a new design system. It should make the
current frontend more useful by adding a reusable starter console model, tests,
and docs alignment.

## Frontend Design

Add a starter console section to the Overview page, above or immediately after
the operating-model explanation. It should be dense, operational, and concrete:

- Starter status summary:
  - `Hosted reference app`: ready
  - `Fake provider mode`: ready
  - `Generated headless surfaces`: ready
  - `Client fork packet`: generated by command
  - `Live provider setup`: client-specific
- Day-0 command loop:
  - `pnpm template:quickstart -- --blueprint source-grounded-gtm-brain --name "Client Brain" --write`
  - `pnpm template:doctor -- --mode fake`
  - `pnpm template:seed-demo -- --blueprint source-grounded-gtm-brain --write`
  - `pnpm template:add-client-domain -- --name customerContext --write`
  - `pnpm template:handoff -- --mode fake --write`
- Starter proof points:
  - Brain/source context
  - Workflow graph and receipt
  - API/CLI/MCP registry
  - Provider posture
  - Security and CI gates

This slice can render the console as document sections instead of new cards.
That keeps the visual work small and avoids fighting Notion Kit before the
starter story is stable.

## Generator And Docs Design

Clarify the quickstart dependency order:

- `template:quickstart -- --write` creates `template-instance.json`.
- `template:doctor -- --mode fake` expects `template-instance.json`.
- Non-`--write` commands preview output and do not change the repo.

Update maturity/backlog language so it no longer contradicts the merged
baseline. The maturity model should describe the current state as:

- L0-L4 are materially implemented for this template baseline.
- L5 is client-fork-specific and requires live provider credentials, live smoke,
  and client handoff evidence.

The porting backlog should remain useful as an inventory, but it must state that
older per-item statuses can lag current implementation and that the current
readiness commands and maturity model are authoritative.

## Testing

Add focused tests that prove:

- The sample app exposes the starter console sections and Day-0 commands.
- The quickstart docs mention `--write` before doctor.
- The maturity model names the current baseline honestly and keeps L5 as
  client-specific.

Use existing test patterns:

- `apps/web/src/sample/templateData.test.ts` for sample page content.
- `tooling/quality/check-docs-freshness` or a small existing docs test if
  available for docs claims.
- `pnpm --dir apps/web test -- src/sample/templateData.test.ts`
- `pnpm check:docs-freshness`

## Non-Goals

- Do not replace Notion Kit.
- Do not introduce Saas UI yet.
- Do not build live provider setup.
- Do not add auth, billing, email, storage, or LLM live credentials.
- Do not redesign every route.

## Acceptance Criteria

- The Overview page has a clear starter console section with status, Day-0 loop,
  and proof points.
- Docs explain the actual command order without implying `doctor` works before
  an instance file exists.
- Maturity/backlog docs no longer contradict the merged effectified baseline.
- Focused app/docs tests pass.
- Full verification passes before merging.
